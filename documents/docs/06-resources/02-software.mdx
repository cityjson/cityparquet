Use the Rust implementation to create and read CityParquet packages, DuckDB to
query them, and the 3D extension to measure their geometry. The
[SQL playground](/playground) runs the DuckDB extensions in your browser.

The tools are experimental and the format is still a draft. APIs and output
schemas may change; validate results before relying on them in a production
workflow.

| Tool | Use it for | Availability |
| --- | --- | --- |
| **cityparquet-rs** | Convert city models, read packages, export CityJSON, and check round trips | Rust library and CLI in the monorepo |
| **DuckDB CityJSON** (`cityjson`) | Read and write city-model formats; create and edit CityParquet packages in SQL | DuckDB community extension |
| **DuckDB 3D** (`three_d`) | Validate solids and measure volume, area, height, and 3D distance | DuckDB community extension |
| **CityParquet MCP server** | Give an AI client documentation, dataset inspection, and bounded SQL queries | Local stdio server built from source |
| **CityLake** | Manage CityParquet datasets through DuckLake and an HTTP API | Development-stage Rust service in the monorepo |

## Rust library and CLI

**cityparquet-rs** is the reference reader and writer. It converts CityJSON,
CityJSONSeq, and CityGML into a package of Parquet files, with one object table
per CityGML module and one row per city object. Geometry is stored as WKB in
LoD-specific columns, paired with the semantic information needed to reconstruct
the model.

The CLI provides four commands:

| Command | Purpose |
| --- | --- |
| `convert` | Convert CityJSON, CityJSONSeq, or CityGML into a CityParquet package |
| `export` | Export a package to CityJSON or CityJSONSeq |
| `compare` | Compare CityJSON/CityJSONSeq datasets for semantic equality |
| `bench` | Measure writer configurations and round-trip behaviour |

From `lib/cityparquet-rs/` in the
[CityParquet monorepo](https://github.com/cityjson/cityparquet):

```sh
cargo run --release -p cityparquet-cli -- convert model.city.jsonl --output city
cargo run --release -p cityparquet-cli -- export city --help
```

Conversion supports Hilbert spatial ordering, configurable row groups and
compression, and partitioning into multiple packages. An LoD0 footprint can be
synthesised when the source has no LoD0 geometry; `--no-lod0` disables that step.

The Rust library also exposes projected reads, attribute queries, and spatial
row-group pruning. Its optional **`object-store` feature** enables asynchronous
queries through the `object_store` interface; these share query logic with the
local reader. This is a library capability, not a promise that every CLI command
accepts remote URLs.

### Current implementation support

These capabilities are present in the implementation. This is a practical
summary, not a certification of complete specification conformance.

| Area | Current support |
| --- | --- |
| Object tables | CityGML module routing, identity and hierarchy columns, typed attributes, structured addresses, and extension data |
| Geometry | WKB columns with explicit LoD suffixes, including `geometry_lod0_0`; geometry properties and bounding boxes |
| Appearance and instances | Material and texture assignments, appearance sidecars, and geometry-template sidecars with LoD-specific geometry |
| Metadata and CRS | Structured `city` footer metadata, GeoParquet `geo` metadata for eligible geometry, PROJJSON CRS information, and a STAC Item in `metadata.json` |
| Bloom filters | On `id`, `feature_id` and high-cardinality string attributes at FPP 0.01, after the last row group; `--no-bloom` turns them off |
| Reading | Arrow record batches, column projection, attribute filtering, bounding-box pruning, bloom-filter pruning for `id`, `feature_id` and string-equality lookups (every filter of a column asked for in one batched range read, which object storage coalesces into few requests; a filter without a declared `bloom_filter_length` is fetched separately), and optional asynchronous object-store access |
| Checking | Semantic comparison and round-trip checks; no standalone Rust `validate` CLI command |

The Rust implementation currently writes WKB geometry. A dataset-level STAC
Collection spanning multiple packages is not generated by the CLI. For schema
requirements, see the [specification](/specification); for measured costs, see
[benchmarks](/benchmark).

[Source and build instructions](https://github.com/cityjson/cityparquet/tree/develop/lib/cityparquet-rs)

## DuckDB CityJSON extension

The **`cityjson`** extension reads, queries, and writes CityJSON, CityJSONSeq,
and FlatCityBuf in SQL. It maps city objects to rows, infers typed attributes,
and exposes geometry and geometry properties in per-LoD columns. It supports
streaming CityJSONSeq and remote sources, with projection and supported predicate
pushdown; FlatCityBuf reads can use its spatial and attribute indexes.

```sql
INSTALL cityjson FROM community;
LOAD cityjson;

SELECT object_type, count(*)
FROM read_cityjsonseq('https://cityjson.open3d.city/cityjsonseq/delft.city.jsonl')
GROUP BY object_type;
```

The extension also manages **complete CityParquet packages** as DuckDB schemas:

- `cityparquet_read` loads a package and `cityparquet_write` writes a schema back
  to a package with its metadata and sidecars.
- `cityparquet_init` registers tables; the `insert_*` operations import source
  objects into the appropriate module tables.
- Delete, merge, and reconcile operations maintain object relationships and
  derived values.
- `cityparquet_validate`, `cityparquet_orphans`, and `cityparquet_vacuum` check
  structure and manage unreferenced sidecar rows.

`cityparquet_write` writes Parquet bloom filters under its `bloom` option (on by
default). DuckDB writes a filter only for a dictionary-encoded column chunk and
applies its dictionary and bloom options to a whole file, so the extension
writes each object table with 122 880-row row groups and a dictionary cut-off of
the same size, under an 8 MiB cap on a string dictionary page. Eligibility is
therefore conditional on the chunk actually being dictionary-encoded, not a
fixed column list — which excludes a type whose writer never uses a dictionary,
Boolean among them, PLAIN and unfiltered however small its vocabulary. The
dictionary-page cap restricts the rest: across a full row group it works out at
roughly 68 bytes per row for a near-unique column, so `id`, `feature_id` and
ordinary identifier-shaped attributes stay far below it and carry filters, as
the
[recommended defaults](/specification/metadata#recommended-writer-defaults-informative)
prescribe — but a high-cardinality string wider than that is written PLAIN and
carries none, and a compact WKB geometry or JSON column can stay under the cap
and carry one, in any row group rather than only a short trailing one.

On the packages measured so far the filtered set has been a superset of the
Rust writer's, and wider than the string columns: on the delft package (2 231
rows, one row group) 68 of 115 column chunks carry a filter — the numeric and
temporal attributes, the `bbox` leaves, the elements of list columns and the
geometry columns among them. That is an observation on those data, not a
property guaranteed for any input. Sidecars carry none. DuckDB consults the
filters itself for `=` and `IN` predicates, including those pushed down from a
join.

Use the package-writing API when you need the complete package contract. A
standalone `COPY ... TO (FORMAT PARQUET)` is a table export and does not, by
itself, assemble the package's metadata and sidecars.

Edits to a loaded schema use DuckDB transactions. Persisting a package back to
separate files does not make CityParquet a transactional storage format.

## DuckDB 3D extension

The **`three_d`** extension adds `SOLID_3D` and `GEOM_3D` types for processing
3D geometry in SQL. It accepts the WKB and geometry-properties pair stored by
CityParquet, so the same geometry operations work on a package or on rows read
by `cityjson`.

```sql
INSTALL three_d FROM community;
LOAD three_d;
```

Its functions cover solid validation, volume, surface and footprint area,
height, distance, transformations, and geometry serialisation. For example,
`ST_3DFromWKB` constructs a solid, `ST_3DValidationReport` describes its validity,
and `ST_3DVolume` measures its enclosed volume. `ST_3DTryFromWKB` provides a
nullable construction path for data that may contain invalid geometry.

The extension reports invalid geometry rather than silently repairing it. Its
`ST_3D*` naming allows it to coexist with DuckDB's `spatial` extension; it is a
curated set of 3D operations, not full PostGIS compatibility.

[Community registry](https://duckdb.org/community_extensions/extensions/three_d)
· [Tutorial](/tutorials/duckdb-3d)
· [Source and function reference](https://github.com/cityjson/duckdb-3d)

## CityParquet MCP server

The MCP server connects an AI client to the specification, the DuckDB extension
references, and a DuckDB query engine. It can search and read documentation,
describe a remote dataset, and execute SQL with limits on the returned rows and
cell sizes.

It runs locally over **stdio** after building `ai/mcp/`. The server supports an
optional sandbox configuration; there is no hosted endpoint or published
installation package in this repository's setup.

[Setup and client configuration](https://github.com/cityjson/cityparquet/tree/develop/ai/mcp)

## CityLake

**CityLake** is a development-stage service for managing CityParquet datasets
in a DuckLake catalogue. It combines DuckDB, the `cityjson` package operations,
and a Rust HTTP API for ingestion, queries, edits, package export, validation,
and maintenance.

It is a separate runtime layered on CityParquet: querying a published
CityParquet file does not require CityLake or a running server.

[Source](https://github.com/cityjson/cityparquet/tree/develop/lib/citylake)

## Using existing Parquet tools

A CityParquet object table is a Parquet file. DuckDB, Arrow, pandas, and other
Parquet readers can inspect its columns without a CityParquet-specific reader.
Interpreting the full 3D model still requires its geometry properties, hierarchy,
and sidecars; a generic table reader does not reconstruct those semantics for
you.

GeoParquet-compatible geometry columns, such as LoD0 footprints, work with tools
that understand their WKB types. The 3D solid encodings go beyond that shared
vocabulary and need a suitable 3D reader, such as `three_d`.
