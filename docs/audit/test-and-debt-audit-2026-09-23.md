Scope, in priority order: `lib/cityparquet-rs`, `lib/duckdb-3d`,
`lib/duckdb-cityjson`. This is an audit only: no test or source file is changed.

## 1. Summary

## 2. Architecture map

### `lib/cityparquet-rs` (Rust, three crates)

Crate direction is clean and acyclic: `cityparquet-cli` → `cityparquet`
(core) → `cityparquet-schema`. The schema crate has no `arrow-array` or
`parquet` dependency, and `just isolation` enforces that.

Inside `cityparquet` (core, 33 top-level modules, ~55k lines including tests)
the **production** import graph is mostly layered. It was derived from
`crate::…` paths and `use crate::{…}` groups, excluding `#[cfg(test)]` modules
and comments. `wkb_read`, `wkb_write`, `recipe`, `order` and `address` import
nothing from the crate, and the read path
(`reader` → `decode` → `query_core` → `query` → `query_async`) is acyclic.
There is **one strongly connected cluster**, on the write/export side:
`{source, citygml, export, encode, scan, lod0, appearance}`. It comes from
three back-edges:

| Back-edge                    | Cause                                                                                                                                                                                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `export` ↔ `citygml::writer` | `export` dispatches to the CityGML writer, and the writer imports `export`'s `pub(crate)` helpers (`partition_shells`, `shell_faces`, `appearance_columns`, `nest_by_shells`, …). Shared WKB-to-CityJSON-structure decoding lives in the export module |
| `encode` ↔ `lod0`            | `lod0` calls `encode::values_nesting_depth` and `encode::flatten_values`, and `encode` calls `lod0` synthesis                                                                                                                                          |
| `encode` ↔ `appearance`      | the appearance interner imports encode helpers, and encode imports the interner                                                                                                                                                                        |

`source` → `citygml` (reader) is a legitimate edge. It only closes the loop
because the CityGML reader and writer share one parent module.

Public interfaces: `package::convert(&ConvertOptions)`,
`export::export(&ExportOptions)`, `compare`, `query`/`query_async`, and the
`CityParquetReaderBuilder` extension trait on Parquet's `ArrowReaderBuilder`.
That trait is the **only** `pub trait` in the core crate. Every other seam is a
concrete type or free function. `Source` is one struct that switches on a
`SourceFormat` tag and on which optional field is populated (`doc`, or
`buffered` for in-memory merge/partition input), rather than a trait with one
implementation per input. Package output always goes to a local directory:
the write path (`package`, `sidecar`, `partition`, `stac`) calls `std::fs`
directly, and `object_store` is used only by the feature-gated async query
path. `lib.rs` exports 28 of the 33 modules as `pub`, so the crate's public
surface is effectively its whole internal layout.

### `lib/duckdb-3d` (C++ DuckDB extension, ~7k lines)

There are two layers, and the dependency points the right way. `src/kernel/`
(WKB parsing, the solid model, validation, measurements, triangulation, CRS)
includes no DuckDB headers. `src/functions/` holds the DuckDB scalar-function
bindings and depends on `kernel/`. Tests are split into `test/cpp` (kernel
unit tests) and `test/sql` (SQLLogic, 33 files, ~400 records).

### `lib/duckdb-cityjson` (C++ DuckDB extension, ~22k lines excluding the generated 29k-line EPSG table)

All code sits in one flat `src/cityjson/` namespace, with 49 headers. It handles
format I/O for CityJSON, CityJSONSeq, FlatCityBuf, OBJ, glTF and GeoParquet,
the CityParquet package write/insert/merge/delete/validate operations, WKB, and
appearance. `copy_function.cpp` (1.7k lines) and `cityjson_types.cpp` (1k)
are the hubs. Tests are `test/sql` (70 files, ~1.3k SQLLogic records),
`test/cpp` (9) and `test/wasm`.

_Detailed findings follow in the per-module sections._

### 3.1 `lib/cityparquet-rs`

#### Inline unit tests (`src/**`) and `crates/schema/tests`

Scope: 381 inline core unit tests (355 s CPU), 100 schema unit tests (~25 s), schema/tests (2), cli inline (3).
CPU cost is concentrated: `compare::tests` 167 s / 22 tests, `query_async::tests` 128 s / 12 tests,
`sidecar::tests` 26 s / 25, `cityparquet_schema::crs` 23 s / 11, `partition::tests` 13 s / 8. Everything
else together is < 20 s.

**Runner caveat.** The timings come from `cargo nextest`, which runs one process per test, so a `OnceLock` / `LazyLock` cache is rebuilt in every test. The repository's gates (`lib/cityparquet-rs/justfile:31`, `.github/workflows/rust.yml:189`) use plain `cargo test`, which runs one process per test binary. There a `LazyLock` fixture is built once per binary. Where this report proposes a shared `LazyLock` fixture, it saves time under `cargo test`. The **Merge** proposals save time under both runners. The schema `crs` cost (T-RS-U-08) is almost entirely a nextest artefact.

### 3.2 `lib/duckdb-3d`

#### Measured cost

- **Binary freshness:** `build/release/test/unittest` and `build/cpp_tests/three_d_unit_tests` were built 2026-08-24 20:13/20:14. One source commit has landed since (`2cdecc8 feat(wkb): the single-argument constructors take GEOMETRY as well as BLOB`), so the timings and pass results below are **one commit behind HEAD**. Nothing was rebuilt.
- **C++ kernel suite:** 179 test cases, 547 assertions, all pass, **0.29 s wall**. `--durations yes`: slowest is `CrsTransform throws on an unknown CRS` at 0.014 s; everything else is 0.000 s.
- **SQL suite:** 33 files, each run separately with `THREE_D_TEST_FIXTURES=1`, **4.3 s total**. About 0.09 s per file is process start. Slowest: `postgis_oracle.test` 0.50 s, `cityjson_3dbag_attributes.test` 0.30 s (skipped), `st_transform.test` 0.24 s (PROJ database open), `fixtures_gated.test` 0.17 s. Everything else takes 0.09–0.15 s.
- **Skips / flakiness markers:** 5 files `require cityjson` (`cityjson_3dbag_attributes`, `cityjson_delft_remote`, `cityjson_hollow_solid`, `cityjson_interop`, `cityjson_multisolid`) and 1 `require spatial` (`spatial_coexist`) skip under this runner, as CLAUDE.md says to expect. `cityjson_delft_remote.test` fetches a remote URL, so it is the only network-dependent (potentially flaky) test. 30 files `require-env THREE_D_TEST_FIXTURES`, so running the binary without that variable silently skips them. No `skipif`/`mode skip`/`halt` markers were found.
- **Consequence:** runtime is not a cost axis in this repository. Deleting every candidate below saves well under 1 s. The cost of keeping them is **maintenance**: duplicated fixtures, and assertions that pin internals, which a refactor has to rewrite.

#### Kernel interfaces

The kernel has **no interfaces**. `grep virtual src/kernel src/include/kernel` finds nothing. It is made of free functions over concrete value structs: `SolidModel` (`solid_model.hpp`) and `GeomModel` (`geom_model.hpp`). For a geometry kernel over value types, that is appropriate, so no "add an interface" item is raised. The kernel never includes DuckDB headers, and PROJ is correctly hidden behind opaque handles (`crs_transform.hpp:39-40`, `crs_transform.cpp:5-6`). The real replaceability problems are listed below: logic sitting on the wrong side of the kernel/SQL line (D-3D-01, D-3D-06), and two parallel stacks (D-3D-03, D-3D-05).

## 4. Kept, and why

**`lib/cityparquet-rs`**

- **The fast `compare.rs` normalisation tests** (`compare_realigns_solid_semantics_and_material_for_a_degenerate_face`, `…dangling_material_index_at_a_dropped_position`, `a_degenerate_middle_hole_canonicalises_…`, `a_uv_shortfall_ring_does_not_pad_…`, `normalise_geometry_realigns_multisolid_…`). They call the private `normalise_geometry` or use small derived fixtures, but each pins a subtle equivalence rule of the comparator that caused real false passes or false failures on 3DBAG data. They run in ~0.1 s each. (The two 4 s siblings are cost-only modifications; see T-RS-U-04.)
- **`partition.rs` unit tests** (T-RS-U-11 only merges them). They test the pure `pub fn assign_partitions` / `repair_reference_locality` directly, which is the right boundary, at 1/5 the cost of the `partition_real_data.rs` integration tests that repeat them through a full convert.
- **`query_async.rs` I/O-shape tests** (`the_async_prune_fetches_every_filter_with_one_ranged_call`, `a_filter_without_a_declared_length_falls_back_…`). The request-count contract (one ranged call for every Bloom filter) is the point of the async path, and no sync test can observe it. The `RangeCallCounter` wrapper is a thin test double over a real `ParquetObjectReader`, not a mock that verifies itself.
- **`cli/src/main.rs::cli_definition_is_valid`** (`Cli::command().debug_assert()`). It is clap's documented way to catch conflicting argument definitions and costs 0.03 s.
- **`variant.rs` error-string assertions** (`only_zstd_takes_a_level`, `duplicates_malformed_suffixes_…_with_the_grammar`). They assert that the message contains the offending id and the `GRAMMAR` constant. For a CLI and benchmark variant grammar, that text is the user-facing contract, not an incidental string. (`wkb_read.rs`'s checks already match case-insensitively on one token such as "unclosed" / "trailing", which is acceptable.)

**`lib/duckdb-3d`**

- **`test/sql/postgis_oracle.test`** (0.50 s, the slowest file, 83 assertions against the frozen `test/data/postgis_oracle/golden*.csv`): the only external oracle. It catches wrong answers that self-consistent kernel tests cannot, because a kernel test's expected value is the author's own arithmetic.
- **`test/sql/metamorphic_transforms.test`, `st_3d_transforms.test`, `geom_3d_transforms.test`:** these look like kernel math tested through SQL, which would normally make them deletion candidates. They are currently the **only** coverage of translate/scale/rotate, because that math lives in `src/functions/transforms.cpp` (D-3D-01). Keep them until D-3D-01 moves the math into the kernel and adds C++ tests. After that, reduce them to one binding check per function plus the metamorphic properties.
- **Far-from-origin precision cases** (`test_measurements.cpp:201`, `:251`; `test_validation.cpp:261`; `test_triangulation.cpp:65`; `test_geometry_math.cpp:40`): these look like excessive splitting of "volume is right". Each targets a distinct cancellation bug that shows up only at real-world coordinates (for example RD New / 3DBAG), which is exactly the data this stack carries.
- **Crafted-malformed payload rejections** (`test_payload.cpp:127-232`, `test_geom_payload.cpp:48-95`): this is the only place a hostile BLOB cast to `SOLID_3D`/`GEOM_3D` is tested before its offsets are used as raw indices by every reader.
- **One smoke query per SQL function** (for example `st_3d_measurements.test`: tetra volume 1/6, footprint 0.5, NULL propagation, `ST_3DVolume` raising on an open shell): these repeat kernel values but are the binding contract. They are cheap and belong in SQL per CLAUDE.md.

#### D-3D-01 — Geometry math and cache-invalidation rules live in the SQL layer (boundary violation)

- **Location:** `lib/duckdb-3d/src/functions/transforms.cpp`. Translate for SOLID_3D is at 32-90 (vertex shift plus a hand-edited bbox at 71-76). Scale is at 200-257 (with `ValidateSolidModel` at 243). The rotation matrix is at 260-290 (`RotateSolidBlob`) and duplicated almost verbatim at 313-340 (`RotateGeomBlob`). The reprojection re-validation rule is at 368-388 (`ReprojectPayloadBlob`).
- **Problem:** CLAUDE.md says "Keep the SQL/vectorized layer separate from the geometry kernel". Here the actual geometry (affine maps), and the rules about which cached state (bbox, validation, triangulation) each transform invalidates, are written inside DuckDB executor loops. The solid and geom variants each carry their own copy.
- **Impact:** testability: translate/scale/rotate have **zero** C++ tests, and the only coverage is three SQL files (see "Kept" above). Correctness: the invalidation policy is spread across three functions, so a new cached field (for example a future triangulation-orientation flag) has to be remembered in each. Changeability: a WASM or non-DuckDB consumer cannot reuse the transforms.
- **How to fix:**
  1. Add `src/include/kernel/affine.hpp` / `src/kernel/affine.cpp` with `enum class Axis {X,Y,Z}` and `void Translate(std::vector<Vertex3D>&, double dx, double dy, double dz)`, `void Scale(std::vector<Vertex3D>&, double sx, double sy, double sz)`, `void Rotate(std::vector<Vertex3D>&, double radians, Axis)`.
  2. Add model-level wrappers that own the invalidation policy: `void Apply(SolidModel&, const AffineOp&)` (rigid → `ComputeBBox()`; non-rigid → `ComputeBBox()` + `ValidateSolidModel`) and `void Apply(GeomModel&, const AffineOp&)`. Add `void Reproject(SolidModel&, const CrsTransform&)` with the same rule.
  3. Reduce every `ST_3D{Translate,Scale,Rotate*,Transform}` executor to deserialize → `Apply` → serialize.
  4. Add C++ tests on `Apply`: rigid motions preserve the validation flags and volume; a zero scale factor produces a degenerate face; a negative factor recomputes the bbox. Then trim the SQL transform tests to bindings plus the metamorphic properties.
- **Effort:** M
