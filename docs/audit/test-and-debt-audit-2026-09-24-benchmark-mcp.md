# Test-pruning and architecture-debt audit, addendum: benchmark and MCP — 2026-09-24

This addendum applies the method of
[`test-and-debt-audit-2026-09-23.md`](test-and-debt-audit-2026-09-23.md)
(same categories, fields and decision criterion) to four areas that audit did
not cover:

- `benchmark/readbench`
- `benchmark/databases`
- `benchmark/plot` and `benchmark/scripts`
- `ai/mcp`, with `ai/plugin` checked for drift only

This is an audit only: no test or source file is changed. The decisions
recorded in the main report apply here too: the gate uses `cargo nextest`, and
shared fixtures must be on-disk caches.

### Decisions taken after the audit (2026-09-24)

These override anything below that conflicts with them:

- **`bbox-Npct` is an area window in both harnesses (D-DB-01).** It is the
  fraction of the dataset's x/y area, which is what `databases` already uses.
  - readbench's `params::window_for_target` (a row-count target) changes to
    the area window.
  - The `databases` docstring that claims the two harnesses match becomes true.
  - `READ_BENCHMARK.md` and the plot labels change with it: selectivity then
    varies by dataset, and the realised row fraction must be reported next to
    the tag.
  - Both harnesses must anchor the window the same way. `databases` uses the
    lower-left corner.
- **FlatCityBuf's `bbox-query` must read the features it finds (D-RB-11).**
  It reads them as FlatBuffers features, without decoding them to in-memory
  CityJSON. Counting R-tree hits alone is not enough.
- **Delete the ordering, scaling-read and write-bench pipelines (D-PL-05)**,
  with their recipes, prep loaders, committed result directories and fixtures.
- **The live-host MCP tests run in CI (D-MCP-02).** Splitting them into their
  own script (`test:live`) is still useful locally, but CI runs both the
  offline and the live suites as required checks.

- **The † and ≈ figure markers were removed on purpose (D-PL-01).** Delete
  the dead `grain_comparable`/`below_floor` computation from `prep.py` and the
  text in DESIGN.md, the prep docstring and the fixture README that describes
  the markers. The caveats stay as prose on the HTML page.
- **`time_s` is the mean in both harnesses (D-DB-02).** readbench switches
  from the median. The dispersion column next to it must match: `time_mad_s`
  is currently measured around the median, so rename it or replace it (for
  example with a standard deviation), and say which in `READ_BENCHMARK.md`
  and the `databases` README. Fix T-DB-08 so its inputs have different means
  and medians.
- **T-RB-08 and T-RB-10 are approved for deletion.**

Where the time goes:

- **Debug-profile `convert(delft.city.jsonl)`** costs ~4.5 s each (the whole of
  `params::scan_row_bboxes_returns_one_box_per_row_and_their_union`, 4.8 s, is one
  convert plus one scan). It runs **~22 times**: 14× in `tests/coordinator.rs`,
  3× `tests/params.rs`, 4× `tests/variants.rs` (`prepared_delft`), 1× each in
  `readbench_smoke.rs` and `cityparquet_http_runner.rs`, 2× `attr_consistency.rs`
  → ~100 s CPU converting the same fixture.
- **Write children** in `variants.rs`: every variant is converted `write_repeat + 1`
  times in a child process (debug build). The four variants tests spawn 22 write
  children between them (6 + 4+4 + 4 + 4).
- **Two units matter.** Under nextest, wall ≈ the slowest test (the `variants`
  tests). CI (`.github/workflows/rust.yml:189-193`) runs plain `cargo test`, which
  runs the 22 test binaries one after another (tests inside a binary still run on
  threads), so CI test wall ≈ Σ per-binary max ≈ 66 (`variants`) + 21
  (`coordinator`) + 7 (`citygml_runner`) + ~25 (the rest) ≈ 120 s, on a 2-core
  runner more. Savings are quoted as nextest wall and CPU.

##### D-RB-01 — `coordinator::run` is a 580-line god function; the scenario→measurement plan is not a unit

- **Location:** `benchmark/readbench/src/coordinator.rs:201-780` (whole `run`); scenario expansion `:514-691`; `run_measurement` (11 args, `#[allow(clippy::too_many_arguments)]`) `:1180-1272`; `run_write` `:1279-1394`.

##### D-DB-07 — Run context travels through `os.environ` and module-level port-to-container maps

- **Impact:** correctness (security drift), testability, dependency direction.
- **How to fix:**
  1. New module `src/egress-policy.ts`: `interface EgressPolicy { admit(host: string, port: number): Promise<{ ok: true; address: string } | { ok: false; reason: string }> }` and `createEgressPolicy({ allowedHosts, resolve = dns.lookup })`; move `isInternalAddress` there.

  3. Better (closes the documented rebinding gap and removes the second enforcement point): route `describe`'s `fetch` through the in-process proxy (undici `ProxyAgent` to `engine.httpProxy`), so Node's fetch and DuckDB's reads share one enforcement point; then `describe` needs only "is this sandboxed", not the host list.
  4. Tests inject `resolve` (stub table) — T-MCP-06 — and an upstream-port override lets one offline positive tunnel test replace the live one (T-MCP-09).
- **Effort:** M
- **Related Part 1:** T-MCP-06, T-MCP-09

##### D-MCP-05 — The hosted server's configuration is untestable top-level code in the entry point, and tests copy it

##### D-MCP-08 — `Engine.close()` closes the connection but never the `DuckDBInstance`

- **Location:** `ai/mcp/src/duckdb.ts:95-98` (instance created, then only `connection` retained), `:188-190` (`close()` → `connection.closeSync()` only). `DuckDBInstance.closeSync()` exists (`node_modules/@duckdb/node-api/lib/DuckDBInstance.d.ts:9`). The pool's memory bound assumes close frees the engine: `ai/mcp/src/pool.ts:53-55` ("so memory stays bounded even while DuckDB frees a large instance") and `:144-150`.
- **Problem:** the instance (buffer pool up to `memory_limit`, 1 GB per engine on the hosted server) is released only when the JS finaliser runs after GC, not when the pool releases the slot. Under load the hosted server can hold more than `size` instances' memory.
- **Impact:** correctness (memory ceiling on Cloud Run).
- **How to fix:** keep `instance` in `createEngine`'s closure and have `close()` call `connection.closeSync(); instance.closeSync();`. A one-line check in `duckdb.test.ts` that a closed engine's instance rejects `connect()` pins it.
- **Effort:** S
- **Related Part 1:** —
- _Confidence: Medium — not measured; based on the node-api surface (README documents only connection disconnect-on-drop)._

##### D-MCP-09 — The hosted image bakes `spatial` (GDAL) although the hosted server must never load it

- **Location:** `ai/mcp/src/bake.ts:15` (`extensionsFromEnv(process.env.CITYPARQUET_MCP_EXTENSIONS)` → `DEFAULT_EXTENSIONS`, which includes `spatial`, `src/duckdb.ts:16,36`); `ai/mcp/Dockerfile:15-17,31` sets no `CITYPARQUET_MCP_EXTENSIONS`, so `node dist/bake.js` installs `httpfs,cityjson,three_d,spatial` into `/opt/duckdb-extensions`.
- **Problem:** the public container carries the one extension whose HTTP client bypasses the egress proxy. It is not loadable today — **probed** (read-only, temp dir): with `spatial` baked into the extension directory, a sandboxed `HOSTED_EXTENSIONS` engine locked to the proxy answers `LOAD spatial` (and `LOAD '<path>'`) with `Permission Error: File system LocalFileSystem has been disabled by configuration`, `ST_Read('/vsicurl_streaming/…')` is `Catalog Error`, and the local victim server recorded no hit. So the only barrier is `disabled_filesystems` (not `autoload_known_extensions`/`allow_community_extensions`, which do not govern an explicit `LOAD` of a core extension), and no test pins it. Defence in depth, plus a larger image and a slower build.
- **Impact:** security posture (defence in depth), image size.
- **How to fix:** 1. Give `bake.ts` the hosted default: `extensionsFromEnv(env, HOSTED_EXTENSIONS)` (with D-MCP-05's `fallback` parameter), or set `ENV CITYPARQUET_MCP_EXTENSIONS=httpfs,cityjson,three_d` in the runtime stage before the bake. 2. Add `["loading an extension from disk", "LOAD spatial"]` to the `blocked` table in `test/duckdb.test.ts` on an engine brought up without `spatial` in a directory that holds it.
- **Effort:** S
- **Related Part 1:** —
