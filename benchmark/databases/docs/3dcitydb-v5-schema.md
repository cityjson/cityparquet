## Engine version

`<pg>-<postgis>-<citydb>`), pinned deliberately instead of the untagged

identical, not just the `postgresql.conf` tuning on top of it:

This matches `cjdb-db` (`docker.io/postgis/postgis:16-3.4`) exactly —

See `cjdb-schema.md`'s "Engine version" section for the cjdb-side values.

### Resource limits — measured, not assumed

`compose.yml`'s `deploy.resources.limits` (16 cpus / 32G) is a Compose
`deploy:` block, whose support outside Swarm is inconsistent across
Compose implementations and was suspected of being silently ignored by
podman-compose. Verified directly, on both running containers, rather
than by re-reading the config:

- `nproc` inside both containers reports **128** (the host's full core
  count) — `nproc` reflects CPU *affinity* (the cgroup `cpuset`
  controller), which the limit does not touch, so this number alone does
  **not** show whether the limit binds.
- `/sys/fs/cgroup/cpu.max` inside both containers: **`1600000 100000`**
  (a 1,600,000µs quota per 100,000µs period — 16 cores' worth of CPU
  *bandwidth*, the controller that actually caps throughput).
- `/sys/fs/cgroup/memory.max` inside both containers: **`34359738368`**
  bytes, exactly 32GiB.
- `podman inspect <container> --format '{{.Config.CreateCommand}}'` shows
  podman-compose 1.6.0 translated the Compose `deploy:` block into native
  podman flags at container-creation time: **`--cpus 16.0 -m 32g`** (also
  reflected in `HostConfig.NanoCpus = 16000000000`, `HostConfig.CpuQuota
  = 1600000`, `HostConfig.Memory = 34359738368`) — identical on both
  `citybench-cjdb` and `citybench-citydb`.
- **Enforcement was confirmed under load**, not just inferred from the
  cgroup files: 32 concurrent CPU-bound busy-loop workers were started
  inside each container for 5 seconds. `cpu.stat`'s `nr_throttled` /
  `throttled_usec` counters, both 0 at baseline, rose to **50 throttled
  periods and ≈53s of accumulated throttled time on `cjdb-db`**, and to
  **50 throttled periods and ≈74s on `citydb-db`**, over that same 5
  second wall-clock burst — direct evidence the kernel's CFS bandwidth
  controller is actively capping both containers to the 16-core-worth
  quota, symmetrically.

**Conclusion: the limit is not silently ignored.** podman-compose 1.6.0
does honour `deploy.resources.limits` in this environment, translating it
to `--cpus`/`-m` at container-creation time, and the kernel enforces it
under load exactly as configured, identically on both services. No change
to `compose.yml` was needed. `nproc` reporting 128 (rather than 16) inside
the container remains true and is worth knowing about separately: it is
the reason `citydb-tool import cityjson`'s default thread count (which
reads `nproc`) had to be capped explicitly with `--threads=4` (see
"Counting granularity" section's import notes and the fix report) — that
default reads CPU *affinity*, not the bandwidth quota, so it is unaffected
by whether the `--cpus` limit binds.

## Counting granularity

This section resolves the harness's central blocking item: what predicate
restricts `citydb.feature` to CityJSON **CityObject** granularity, so that
3DCityDB's counts are comparable with cjdb's and with the source ground
truth. Derived empirically against `data/delft.city.jsonl`
(1115 top-level features / 2231 CityObjects) after import via
`citydb-tool import cityjson --threads=4` into the `citydb` schema (SRID
7415), and re-validated after pinning the image to
`3dcitydb-pg:16-3.4-5.1.2-alpine` for engine parity with cjdb (see "Engine
version" above) — table/column layout, class breakdown and all counts
below are unchanged from the original capture against `5-alpine`
(3DCityDB 5.1.3 / PostgreSQL 18 / PostGIS 3.6), confirming the predicate
does not depend on the engine version.

### Recommended predicate — use this one

**Every later `count` and `full-read` query for 3DCityDB in this harness
must use this predicate:**

```sql
WITH RECURSIVE class_chain AS (
    SELECT id, superclass_id, id AS leaf_id FROM citydb.objectclass
    UNION ALL
    SELECT oc.id, oc.superclass_id, cc.leaf_id
    FROM citydb.objectclass oc
    JOIN class_chain cc ON oc.id = cc.superclass_id
),
descends_from_space_boundary AS (
    SELECT DISTINCT leaf_id FROM class_chain WHERE id = 13  -- AbstractSpaceBoundary
)
SELECT count(*) AS city_object_rows
FROM citydb.feature f
JOIN citydb.objectclass oc ON oc.id = f.objectclass_id
WHERE oc.is_toplevel = 1
   OR f.objectclass_id NOT IN (SELECT leaf_id FROM descends_from_space_boundary);
-- => 2231
```

This is the `is_toplevel = 1 OR NOT <descends from AbstractSpaceBoundary>`
form. It is recommended over the two narrower alternatives given later in
this section (a bare "exclude descendants of id 13" predicate, and a
dataset-scoped `NOT IN (709, 710, 712)` list) because it is the only one
of the three that survives the ReliefFeature anomaly documented below:
objectclass id `500` (`ReliefFeature`) is itself a descendant of id `13`
in this schema despite being a genuine, `is_toplevel = 1` CityObject type.
Excluding by `is_toplevel = 1 OR NOT <descends from 13>` cannot drop a
class the schema itself flags as top-level, so it is safe to reuse
against a dataset this fixture doesn't exercise (terrain, transportation,
etc.) without first checking whether that dataset trips the same
anomaly. The two narrower forms are offered afterwards only as faster,
narrower alternatives for when they have been independently re-verified
against a given dataset's own ground truth — see "Two narrower
alternatives" below for exactly when each is and isn't safe.

### Why the naive count is wrong

`citydb.feature` holds one row per **feature of any objectclass**, not one
row per CityJSON CityObject. For this fixture the breakdown by
`objectclass_id` is:

| `objectclass_id` | `classname` | `is_toplevel` | rows |
|---:|---|---:|---:|
| 709 | WallSurface | 0 | 3350 |
| 710 | GroundSurface | 0 | 2232 |
| 712 | RoofSurface | 0 | 2232 |
| 901 | Building | 1 | 1115 |
| 902 | BuildingPart | 0 | 1116 |
| — | **total** | — | **10045** |

`WallSurface`, `GroundSurface` and `RoofSurface` are CityGML **semantic
(boundary) surfaces** — in CityJSON these live inside a geometry's
`semantics` block, not as separate top-level entries in `CityObjects`. They
must be excluded. `Building` + `BuildingPart` = 1115 + 1116 = **2231**,
exactly the target.

Two candidate single-column predicates were ruled out first:

- **`count(*)` with no filter**: 10045 — includes the semantic surfaces.
- **`objectclass.is_toplevel = 1`**: 1115 — correctly excludes the
  semantic surfaces, but *also* incorrectly excludes `BuildingPart`
  (`is_toplevel = 0`), which nonetheless is a real CityJSON CityObject (a
  child of `Building`). This is exactly the trap the brief warned about.

**Correction to the brief's stated facts:** the brief's list of confirmed
`objectclass` ids (`901` Building, `902` BuildingPart, `709` WallSurface,
`712` RoofSurface) omits **`710` GroundSurface**, which is also present in
this fixture (2232 rows) and is *also* a semantic surface that must be
excluded. Filtering out only 709 and 712 leaves 10045 − 3350 − 2232 = 4463
— not 2231. GroundSurface must be excluded too.

### Deriving the rule: the class hierarchy

`citydb.objectclass` is a small class-hierarchy table (`superclass_id`
points to the immediate parent). Walking it shows the three semantic
surfaces all descend from objectclass id `13`, `AbstractSpaceBoundary`,
while `Building` and `BuildingPart` descend from id `8`, `AbstractSpace`,
by a different path:

```
709 WallSurface    -> 708 AbstractConstructionSurface -> 14 AbstractThematicSurface -> 13 AbstractSpaceBoundary -> 7 AbstractCityObject
710 GroundSurface  -> 708                              -> 14                        -> 13                      -> 7
712 RoofSurface    -> 708                              -> 14                        -> 13                      -> 7
901 Building       -> 900 AbstractBuilding -> 700 AbstractConstruction -> 12 AbstractOccupiedSpace -> 10 AbstractPhysicalSpace -> 8 AbstractSpace -> 7
902 BuildingPart   -> 900                  -> 700                      -> 12                        -> 10                     -> 8               -> 7
```

This is the structural fact behind the recommended predicate above: **a
`feature` row is a CityObject unless its objectclass, or an ancestor of
it, is `AbstractSpaceBoundary` (id 13)** — *except* that this bare rule
has one known counter-example (`ReliefFeature`, id `500`), which is why
the recommended predicate adds `OR is_toplevel = 1` as a guard. See
"ReliefFeature anomaly" below for that counter-example.

### Two narrower alternatives (not recommended as the default)

Both of these also produce exactly 2231 against `delft.city.jsonl`, and
are recorded because they may be useful — but neither is the predicate to
reach for without re-checking it first.

**1. Bare "exclude descendants of `AbstractSpaceBoundary`", no `is_toplevel`
guard:**

```sql
WITH RECURSIVE class_chain AS (
    SELECT id, superclass_id, id AS leaf_id FROM citydb.objectclass
    UNION ALL
    SELECT oc.id, oc.superclass_id, cc.leaf_id
    FROM citydb.objectclass oc
    JOIN class_chain cc ON oc.id = cc.superclass_id
),
is_space_boundary AS (
    SELECT DISTINCT leaf_id FROM class_chain WHERE id = 13  -- AbstractSpaceBoundary
)
SELECT count(*) AS city_object_rows
FROM citydb.feature f
WHERE f.objectclass_id NOT IN (SELECT leaf_id FROM is_space_boundary);
-- => 2231
```

Only safe when the dataset is known not to contain any class descending
from id 13 that is *also* `is_toplevel = 1` — `ReliefFeature` (id 500) is
the one known instance of this in the current schema. This holds for
`delft.city.jsonl` (buildings only) but is not proven to hold generally —
see "ReliefFeature anomaly" below.

**2. Dataset-scoped concrete id list**, resolving alternative 1 above to
the specific ids present in this one import:

```sql
SELECT count(*) AS city_object_rows
FROM citydb.feature
WHERE objectclass_id NOT IN (709, 710, 712);
-- => 2231
```

Only safe for `delft.city.jsonl` specifically, on this schema version —
it hardcodes the exact semantic-surface ids this one fixture happens to
contain, and would silently miscount if a future import introduces
another semantic-surface subclass (`InteriorWallSurface`, `FloorSurface`,
etc.) not in this list. Re-derive the id list per dataset before reusing
it, the same way this fixture's list was derived (group `feature` by
`objectclass_id`, cross-check the non-toplevel entries against the class
hierarchy).

### ReliefFeature anomaly

`objectclass` id `500`, `ReliefFeature`, is **itself** a subclass of
`AbstractSpaceBoundary` (`superclass_id = 13`) in 3DCityDB v5.1.2 (also
confirmed present in v5.1.3), despite being `is_toplevel = 1` and a
genuine standalone CityJSON CityObject type (`TINRelief` etc.). A bare
"exclude everything under `AbstractSpaceBoundary`" rule (alternative 1
above) would therefore incorrectly drop relief/terrain CityObjects from a
dataset that contains them, even though it is exactly right for a
buildings-only fixture like `delft.city.jsonl` (which contains no relief
features — confirmed by querying for `classname ILIKE '%relief%'` /
`'%tin%'`, zero rows). This is exactly why the recommended predicate at
the top of this section adds `OR is_toplevel = 1`: that guard cannot
exclude a class the schema itself flags as top-level, so it does not
depend on knowing in advance whether a given dataset trips this
anomaly. **Before reusing either narrower alternative against a corpus
dataset that includes terrain, transportation, or other non-building
content, re-run the three-count comparison in this section against that
dataset's own ground truth** (`citybench.params.derive(...).total_city_objects`)
rather than assuming the Delft-derived predicate transfers unchanged.

## LoD value format (Task 9 finding)

`property.val_lod` does not preserve CityJSON's fractional LoD notation.
`data/delft.city.jsonl` uses `"0"`, `"1.2"`, `"1.3"`, `"2.2"` as `lod`
tags on individual geometries (confirmed by reading the source file
directly), but after `citydb-tool import cityjson --threads=4`,
`citydb.property.val_lod` holds only the **truncated integer tier**:

```sql
SELECT val_lod, count(*) FROM citydb.property WHERE val_lod IS NOT NULL GROUP BY val_lod ORDER BY val_lod;
--  val_lod | count
-- ---------+-------
--  0       |  1115
--  1       |  4929
--  2       |  5117
```

A query for `val_lod = '1.2'` (the brief's literal placeholder, copying
CityJSON's own notation) therefore matches **zero rows** — not an error,
just silently the wrong answer. `citydb-tool`'s CityJSON importer
collapses `"1.2"`/`"1.3"` into `"1"` and (presumably, unconfirmed for this
buildings-only fixture, which has no LoD3/LoD2.3 geometry) `"2.2"`/`"2.3"`
into `"2"`. `sql_citydb.py`'s `lod-extract` therefore targets `val_lod =
'1'`, not `'1.2'`.

Restricting to CityObject-granular features (the "Recommended predicate"
above) matters here too, independently of the granularity predicate's
role in `count`: `property.name = 'lod1Solid'` rows (the CityObject's own
LoD1 solid geometry, one per `BuildingPart`) and `property.name =
'lod1MultiSurface'` rows (the same solid's *boundary surfaces* — i.e. the
`WallSurface`/`GroundSurface`/`RoofSurface` features' own LoD1 geometry)
both carry `val_lod = '1'` and `val_geometry_id IS NOT NULL`. Without the
CityObject-granularity predicate, `val_lod = '1' AND val_geometry_id IS
NOT NULL` matches 4929 rows (1116 `lod1Solid` + 3813 `lod1MultiSurface`,
across `BuildingPart`/`WallSurface`/`GroundSurface`/`RoofSurface`); with
it, exactly 1116 — one `lod1Solid` row per `BuildingPart`, the object-level
answer comparable to cjdb's per-CityObject LoD-presence count.

## Index coverage (Task 9 finding)

`citydb-tool import cityjson` creates 3DCityDB's own fixed set of 16
"content indexes" (`citydb index status`'s term) automatically as part of
import — confirmed by `SELECT count(*) FROM pg_indexes WHERE
schemaname='citydb'` reading **59** immediately after import, before
`citydb index create` is ever invoked, and reading **59** again
(unchanged) after running it — `citydb index create` is a verified no-op
against a freshly-imported schema, not a step this task's `ingest()`
needs to call. Every column this benchmark's scenario queries filter, join
or aggregate on is already covered by one of the 59: `feature_objectid_inx`
(id-lookup, the parent lookup half of hierarchy), `feature_objectclass_inx`
(count, project, attr-filter, semantic-surface, the CityObject-granularity
predicate itself), `feature_envelope_spx` (bbox-query, GIST), `property_
name_inx` (attr-stats), `property_val_geometry_fkx` (lod-extract),
`property_feature_fkx` + `feature_pk` (the rest of hierarchy's join
chain). Confirmed by `EXPLAIN` under default planner settings for every
scenario — see the Task 9 report for the captured plans.
`sql_citydb.index_ddl()` therefore returns an empty list: there is nothing
genuinely missing to add, and adding a same-shape index under a new name
would be a redundant index object inflating `size_bytes`, the class of
error Task 8 warned about for cjdb.
