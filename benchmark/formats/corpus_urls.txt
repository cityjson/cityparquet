# CityParquet benchmark corpus — download URLs
# ============================================
#
# Source: the CityJSON project's own dataset page,
#   https://www.cityjson.org/datasets/
# specifically its "Major City Datasets" table, which publishes nine city
# models converted and hosted by the TU Delft 3D geoinformation group.
#
# SIX of those nine are pinned below. Verified live on 2026-08-23 (HTTP status
# and byte size by streamed GET; content by parsing the downloaded document).
#
# Usage — the usable list is exactly:
#   grep -v '^#' benchmark/formats/corpus_urls.txt
# `scripts/tests/fetch_benchmark_test.sh` requires that list to be the same set
# as `benchmark/scripts/fetch_benchmark.sh`'s CORPUS table, so the two cannot drift.
#
# Ordering: smallest first, so a truncated fetch still leaves a size ladder.
#
# WHY THIS CORPUS. The read benchmark compares EIGHT formats, and a dataset
# that cannot produce all eight contributes a row with a hole in it. These six
# each produce all eight from one source document. That is the whole selection
# criterion, and it is why this corpus replaced a 30-dataset one drawn from the
# city3d STAC catalogue (archived, with its own provenance file, under
# benchmark/formats/archive/2026-08-17-catalogue-corpus/).
#
# WHY CityJSON AND NOT THE PUBLISHED .gml. The cityjson.org table offers a
# matching CityGML file beside every CityJSON one, and it would be preferable
# to measure those originals. NOT ONE of them is readable by this repository,
# which accepts only CityGML 2.0 — checked on 2026-08-23, first 40 KB of each:
#
#   3-20-DELFSHAVEN.xml            17 MB   CityGML 1.0
#   DenHaag_01.xml                 24 MB   CityGML 1.0
#   Vienna_102081.gml              39 MB   CityGML 1.0
#   VM05_2009.gml                  59 MB   CityGML 1.0
#   DA13_3D_Buildings_Merged.gml  618 MB   CityGML 1.0
#   Zurich_Building_LoD2_V10.gml  3.0 GB   CityGML 1.0
#   9-284-556.gml                  56 MB   CityGML 3.0
#   Ingolstadt.gml                 30 MB   CityGML 3.0
#   LoD3_Railway.gml               47 MB   CityGML 2.0  (excluded, see below)
#
# So the `citygml` artefact is SYNTHESISED from the CityJSON by
# `readbench_prepare.sh` (`citygml-tools from-cityjson -v 2.0`). What that
# costs and what it buys is stated in benchmark/formats/READ_BENCHMARK.md's CityGML
# synthesis section; the short version is that deriving every artefact from one
# source is what makes the eight rows comparable, and that the synthesised
# document is close in size to the published original where one exists
# (Rotterdam: 14.0 MB synthesised vs 16.5 MB published).

# --------------------------------------------------------------------------
# PER-ENTRY PROVENANCE
# --------------------------------------------------------------------------
#
# rotterdam_delfshaven.city.json  <- 3-20-DELFSHAVEN.city.json
#   cityjson.org row "Rotterdam". 2,731,804 B. 853 CityObjects, all `Building`,
#   all LoD2. Numeric attribute `TerrainHeight` on all 853. Published as 76%
#   valid. The corpus's small anchor.
#
# ingolstadt.city.json            <- Ingolstadt.city.json
#   cityjson.org row "Ingolstadt". 5,051,369 B. 379 CityObjects — 55 `Building`,
#   1 `BuildingPart`, 323 `BuildingInstallation`, all Building module, so one
#   object table. LoD3 throughout: the corpus's only LoD3 entry, and the reason
#   it is not an all-LoD2 story. Numeric attribute `measuredHeight` covers only
#   the 55 `Building`s (`materialUncertainty` covers 201), so its `attr-stats`
#   row is computed over a minority of rows — do not read it as a whole-dataset
#   aggregate. Published as 70% valid.
#
# vienna_102081.city.json         <- Vienna_102081.city.json
#   cityjson.org row "Vienna". 5,635,634 B. 1,322 CityObjects — 307 `Building`
#   and 1,015 `BuildingPart`, i.e. real parent/child nesting rather than a flat
#   list. 2,204 LoD2 geometries. Numeric attribute `measuredHeight` on 1,102.
#   Published as 98.5% valid.
#
# 3dbag_9-284-556.city.json       <- 9-284-556.city.json
#   cityjson.org row "3DBAG". 7,032,849 B. 2,221 CityObjects — 1,110 `Building`
#   and 1,111 `BuildingPart`. Numeric attribute `b3_h_dak_50p` on all 1,110
#   parents.
#
#   THE ONLY MULTI-LoD ENTRY: LoD 0, 1.2, 1.3 and 2.2, which is why it is in
#   the corpus — it is the only dataset here that exercises CityParquet's
#   per-LoD `geometry_lod*` columns at all. CityGML 2.0 has only integer LoDs,
#   so the synthesised `.gml` collapses 1.2 and 1.3 into a single `lod1Solid`
#   and carries THREE LoDs where every other artefact carries four (verified
#   2026-08-23: lod0FootPrint 1,110 / lod1Solid 1,111 / lod2Solid 1,111 /
#   lod2MultiSurface 4,031). Its `citygml` row is therefore not
#   content-equivalent to its other seven. Disclosed rather than dropped; see
#   benchmark/formats/READ_BENCHMARK.md.
#
# nyc_da13_buildings.city.json    <- DA13_3D_Buildings_Merged.city.json
#   cityjson.org row "New York". 110,083,137 B. 23,777 CityObjects, all
#   `Building`, all LoD2. NO numeric attribute at all, so `just bench` omits
#   its `attr-stats` row. Published as 99.9% valid.
#
# zurich_building_lod2.city.json  <- Zurich_Building_LoD2_V10.city.json
#   cityjson.org row "Zürich". 292,500,409 B. 198,699 CityObjects — 52,834
#   `Building` and 145,865 `BuildingPart`, 145,865 LoD2 geometries. Numeric
#   attribute `Geomtype` on 145,862. The corpus's large anchor, ~108x the
#   smallest entry. Published as 76% valid.

# --------------------------------------------------------------------------
# EXCLUDED — offered by cityjson.org, not measurable here
# --------------------------------------------------------------------------
#
# Both fail gate 2 of benchmark/scripts/fetch_benchmark.sh's verification: a dataset must
# resolve to ONE CityParquet object table, because `cityparquet-readbench`'s
# coordinator refuses a multi-table package outright
# (`locate_cityparquet_table`). Not measured poorly — not measurable.
#
# DenHaag_01.city.json
#   https://3d.bk.tudelft.nl/opendata/cityjson/3dcities/v2.0/DenHaag_01.city.json
#   3,150,451 B, 2,498 CityObjects. 844 `Building` + 1,653 `BuildingPart` —
#   and ONE `TINRelief`. That single relief object puts a `relief.parquet`
#   beside `building.parquet` and disqualifies the whole dataset. Otherwise a
#   good fit (LoD2, four numeric attributes on 1,990 objects), and it would
#   return the moment the coordinator learns to pick a table.
#
# LoD3_Railway.city.json
#   https://3d.bk.tudelft.nl/opendata/cityjson/3dcities/v2.0/LoD3_Railway.city.json
#   4,522,415 B, 121 CityObjects spanning FOURTEEN types across ten CityGML
#   modules: Railway 10, Tunnel 4, TunnelInstallation 8, Building 3,
#   BuildingInstallation 56, Bridge 4, BridgeInstallation 2,
#   BridgeConstructiveElement 3, SolitaryVegetationObject 15, CityFurniture 11,
#   GenericCityObject 2, CityObjectGroup 1, WaterBody 1, TINRelief 1. Ten
#   object tables. It also carries no numeric attribute and only 121 objects,
#   so even single-table it would be degenerate for every selectivity-based
#   scenario. Note this is the ONE cityjson.org dataset whose published `.gml`
#   is CityGML 2.0 and would have needed no synthesis.
#
# The remaining cityjson.org entry, Montréal (VM05_2009.city.json, 5,644,656 B,
# 294 `Building`, LoD2), passes every gate and is simply not pinned: it sits in
# Vienna's size band at the same LoD with NO numeric attribute, so it would add
# a seventh row without adding an axis. Add it to the CORPUS table if a second
# point in that band is ever wanted.
