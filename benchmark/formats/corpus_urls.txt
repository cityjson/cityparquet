# CityParquet benchmark corpus — download URLs
# ============================================
#
# Seven city datasets. Five are pinned from the CityJSON project's own dataset
# page, https://www.cityjson.org/datasets/ ("Major City Datasets", converted and
# hosted by the TU Delft 3D geoinformation group), verified live on 2026-08-23
# and unchanged since. Two — Tokyo (Chiyoda) and Montréal — are derived by this
# project from published sources and hosted on its own mirror; their derivation
# is recorded below so either can be rebuilt byte for byte. The format
# comparison's eighth dataset, the 1,000,001-object 3DBAG slice, is cut by
# `just fetch-scaling-data` from its own pinned source.
#
# Usage — the usable list is exactly:
#   grep -v '^#' benchmark/formats/corpus_urls.txt
# `scripts/tests/fetch_benchmark_test.sh` requires that list to be the same set
# as `benchmark/scripts/fetch_benchmark.sh`'s CORPUS table, which also pins each
# file's byte size and sha256, so the two cannot drift.
#
# THE MIRROR. Every dataset's CityJSON is also served from
#   https://pub-7aad9a74319741828dbafdbf5e2df201.r2.dev/cityparquet-paper/benchmark/cityjson20/<id>.city.json
# and the CityGML 2.0 the benchmark synthesises from it from
#   https://pub-7aad9a74319741828dbafdbf5e2df201.r2.dev/cityparquet-paper/benchmark/citygml20/<id>.gml
# The mirror's CityJSON is byte-identical to the pinned file. Its CityGML is a
# convenience copy: the benchmark keeps synthesising its own `.gml` with the
# pinned citygml-tools, and the two are identical once the tool's per-run
# random `ID_<uuid>` identifiers are masked.
#
# WHY THIS CORPUS. The read benchmark compares FIVE formats — CityGML,
# CityJSON, CityJSONSeq, FlatCityBuf and CityParquet — and a dataset that
# cannot produce all five contributes a row with a hole in it. Each of these
# produces all five from one source document; that is the selection criterion.
#
# WHY CityJSON AND NOT THE PUBLISHED .gml. The cityjson.org table offers a
# matching CityGML file beside every CityJSON one, and it would be preferable
# to measure those originals. NOT ONE of them is readable by this repository,
# which accepts only CityGML 2.0 — checked on 2026-08-23, first 40 KB of each:
#
#   3-20-DELFSHAVEN.xml            17 MB   CityGML 1.0
#   DenHaag_01.xml                 24 MB   CityGML 1.0
#   Vienna_102081.gml              39 MB   CityGML 1.0
#   VM05_2009.gml                  59 MB   CityGML 1.0
#   DA13_3D_Buildings_Merged.gml  618 MB   CityGML 1.0
#   Zurich_Building_LoD2_V10.gml  3.0 GB   CityGML 1.0
#   9-284-556.gml                  56 MB   CityGML 3.0
#   Ingolstadt.gml                 30 MB   CityGML 3.0
#   LoD3_Railway.gml               47 MB   CityGML 2.0  (excluded, see below)
#
# So the `citygml` artefact is SYNTHESISED from the CityJSON by
# `readbench_prepare.sh` (`citygml-tools from-cityjson -v 2.0`). What that
# costs and what it buys is stated in benchmark/formats/READ_BENCHMARK.md's
# CityGML synthesis section; the short version is that deriving every artefact
# from one source is what makes the five rows comparable, and that the
# synthesised document is close in size to the published original where one
# exists (Rotterdam: 14.0 MB synthesised vs 16.5 MB published).
#
# Ordering: smallest first, so a truncated fetch still leaves a size ladder.

# PER-ENTRY PROVENANCE
# --------------------------------------------------------------------------
#
# rotterdam_delfshaven.city.json  <- 3-20-DELFSHAVEN.city.json
#   cityjson.org row "Rotterdam". 2,731,804 B. 853 CityObjects, all `Building`,
#   all LoD2. Numeric attribute `TerrainHeight` on all 853. Published as 76%
#   valid. The corpus's small anchor.
#
# ingolstadt.city.json            <- Ingolstadt.city.json
#   cityjson.org row "Ingolstadt". 5,051,369 B. 379 CityObjects — 55 `Building`,
#   1 `BuildingPart`, 323 `BuildingInstallation`, all Building module, so one
#   object table. LoD3 throughout. Numeric attribute `measuredHeight` covers
#   only the 55 `Building`s (`materialUncertainty` covers 201), so its
#   `attr-stats` row is computed over a minority of rows — do not read it as a
#   whole-dataset aggregate. Published as 70% valid.
#
# vienna_102081.city.json         <- Vienna_102081.city.json
#   cityjson.org row "Vienna". 5,635,634 B. 1,322 CityObjects — 307 `Building`
#   and 1,015 `BuildingPart`, i.e. real parent/child nesting rather than a flat
#   list; 220 of the `Building`s carry no geometry of their own. 2,204 LoD2
#   geometries. Numeric attribute `measuredHeight` on 1,102. Published as
#   98.5% valid.
#
# nyc_da13_buildings.city.json    <- DA13_3D_Buildings_Merged.city.json
#   cityjson.org row "New York". 110,083,137 B. 23,777 CityObjects, all
#   `Building`, all LoD2. NO numeric attribute at all, so the benchmark omits
#   its `attr-stats` row. Published as 99.9% valid.
#
# zurich_building_lod2.city.json  <- Zurich_Building_LoD2_V10.city.json
#   cityjson.org row "Zürich". 292,500,409 B. 198,699 CityObjects — 52,834
#   `Building` (none with geometry of its own) and 145,865 `BuildingPart`,
#   145,865 LoD2 geometries. Numeric attribute `Geomtype` on 145,862. The
#   corpus's large anchor. Published as 76% valid.
#
# tokyo.city.json                 <- PLATEAU Chiyoda-ku, 2025 `bldg` (derived)
#   315,968,009 B, sha256 4a3e2e01bf5136e14f4d43bc993861d6d19234488f2867cc4e83e4d7dd8822ac.
#   3D city model of Chiyoda-ku, Tokyo, PLATEAU, Ministry of Land,
#   Infrastructure, Transport and Tourism (MLIT), Japan — CC BY 4.0. 49,915
#   CityObjects — 38,743 `Building` and 11,172 `BuildingInstallation` — LoD 0,
#   1 and 2 (124 LoD3 installation geometries), textured; 35,067 objects carry
#   an `address`. CRS JGD2011 (EPSG:6697), which declares LATITUDE FIRST: the
#   CityJSON keeps that order, a CityParquet package stores longitude first
#   (READ_BENCHMARK.md, Caveat 22).
#
#   Derivation, in order:
#     1. The 21 `bldg` CityGML tiles of the ward (`533945*_bldg_6697_op.gml`,
#        `533946*_bldg_6697_op.gml`, Last-Modified 2026-03-27); their sha256s
#        are in `benchmark/formats/tokyo_sources.sha256`. The catalogue's
#        feature count, 38,761,
#        describes another revision; these files hold 38,743 Buildings and
#        11,172 BuildingInstallations.
#     2. Texture `mimeType` `image/jpg` rewritten to `image/jpeg`, so every
#        texture gets a valid CityJSON `type`.
#     3. `citygml-tools 2.5.0 to-cityjson --vertex-precision=10` per tile. It
#        skips the `uro` ADE, which it has no extension for: the
#        `buildingIDAttribute`, `buildingDetailAttribute`,
#        `bldgDataQualityAttribute`, `bldgDisasterRiskAttribute` and
#        `bldgKeyValuePairAttribute` groups are absent from the CityJSON.
#     4. `benchmark/scripts/cityjson_merge.py --z-scale 1e-6 <21 tiles, sorted>`
#        — one document, transform scale `[1e-10, 1e-10, 1e-6]`. `z` is
#        re-quantised to 1e-6 m (largest change 0.5 µm) because FlatCityBuf
#        stores vertices as 32-bit integers and a uniform 1e-10 overflows on
#        height.
#   Known wart: `creationDate` values carry the converting machine's UTC
#   offset (`+01:00` or `+02:00`), not the source's.
#
# montreal.city.json              <- Montréal 2020 3D buildings (derived)
#   498,371,022 B, sha256 e54940e3aec2d2e4157b4dc0b5575c903066a2502e7d4a2e99c95e6180fc74cb.
#   Ville de Montréal, "Bâtiments 3D 2020 (maquette LoD2 avec textures)",
#   https://donnees.montreal.ca/dataset/batiments-3d-2020-maquette-lod2-avec-textures
#   (licence https://donnees.montreal.ca/licence-d-utilisation). 31,415
#   CityObjects, all `Building`, LoD 0 (on 31,403) and 2, textured. CRS
#   NAD83(CSRS) / MTM zone 8 (EPSG:2950).
#
#   THIS DATASET IS DERIVED FROM CITYPARQUET, by the author's decision. Its
#   source is this project's own published CityParquet packages of three
#   boroughs (STAC collection
#   https://cityparquet.open3d.city/data/montreal-2020/collection.json,
#   packages at `cityparquet:version` 0.1.0-draft):
#     1. `cityparquet export` (CLI at monorepo commit 2f042db) of the
#        `cote-des-neiges-notre-dame-de-grace`, `outremont` and `ville-marie`
#        packages, one CityJSON document each.
#     2. `benchmark/scripts/cityjson_merge.py --rescale 1e-5,1e-3,1e-6
#        --allow-residual 0.001 --texture-type-from-extension <3 exports,
#        sorted>` — scale refined to `[1e-5, 1e-3, 1e-6]` (exact), textures
#        given type `JPG` from their file extension. Outremont's `y` translate
#        is not a whole number of millimetres from the others', so its
#        vertices shift by up to 0.000849 mm in `y` on merging.
#   The one exception to the preparation chain's rule that nothing derives
#   from CityParquet; READ_BENCHMARK.md, Caveat 14, states what it means.

# EXCLUDED — offered by cityjson.org, not measurable here

#
# Both fail gate 2 of benchmark/scripts/fetch_benchmark.sh's verification: a dataset must
# resolve to ONE CityParquet object table, because `cityparquet-readbench`'s
# coordinator refuses a multi-table package outright
# (`locate_cityparquet_table`). Not measured poorly — not measurable.
#
# DenHaag_01.city.json
#   https://3d.bk.tudelft.nl/opendata/cityjson/3dcities/v2.0/DenHaag_01.city.json
#   3,150,451 B, 2,498 CityObjects. 844 `Building` + 1,653 `BuildingPart` —
#   and ONE `TINRelief`. That single relief object puts a `relief.parquet`
#   beside `building.parquet` and disqualifies the whole dataset. Otherwise a
#   good fit (LoD2, four numeric attributes on 1,990 objects), and it would
#   return the moment the coordinator learns to pick a table.
#
# LoD3_Railway.city.json
#   https://3d.bk.tudelft.nl/opendata/cityjson/3dcities/v2.0/LoD3_Railway.city.json
#   4,522,415 B, 121 CityObjects spanning FOURTEEN types across ten CityGML
#   modules: Railway 10, Tunnel 4, TunnelInstallation 8, Building 3,
#   BuildingInstallation 56, Bridge 4, BridgeInstallation 2,
#   BridgeConstructiveElement 3, SolitaryVegetationObject 15, CityFurniture 11,
#   GenericCityObject 2, CityObjectGroup 1, WaterBody 1, TINRelief 1. Ten
#   object tables. It also carries no numeric attribute and only 121 objects,
#   so even single-table it would be degenerate for every selectivity-based
#   scenario. Note this is the ONE cityjson.org dataset whose published `.gml`
#   is CityGML 2.0 and would have needed no synthesis.
#
# The cityjson.org Montréal entry (VM05_2009.city.json, 5,644,656 B, 294
# `Building`, LoD2) passes every gate and is not pinned: it sits in Vienna's
# size band with NO numeric attribute. The corpus's `montreal` is the 2020
# model of three boroughs above, a different and much larger dataset.
#
# The cityjson.org 3DBAG tile (9-284-556.city.json) is not pinned either: the
# 3DBAG slices cut by `just fetch-scaling-data` stand in for it, at the
# scale that matters.
